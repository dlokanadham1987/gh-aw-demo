0:03 – 0:09 · Mental model

The three commands you'll ever need

# 1. One-time per repo — scaffolding only
gh aw init

# 2. Add a workflow (or hand-write the .md)
gh aw add pr-summarizer

# 3. Every time the .md changes
gh aw compile pr-summarizer

Then it's just git add · git commit · git push. GitHub takes over.

Three commands, in this order. That's the whole CLI for 95% of use cases. "gh aw init" does NOT create workflows — it only sets up the folder structure.
0:03 – 0:09 · Mental model

What runs, step by step

1. Event fires (PR opened, push, schedule, …)
↓
2. GitHub Actions reads *.lock.yml and starts a runner
↓
3. Setup job: pulls your prompt + Claude binary
↓
4. Agent job: Claude reads context, calls allowed tools
↓
5. Safe-outputs: validate what the agent wants to do
↓
6. Conclusion: post the comment / open the PR / etc.
You don't need to memorize the 6 jobs — but it's good to know they exist because the GitHub Actions UI shows them as separate boxes.
0:09 – 0:15 · English, not YAML

The old way

# .github/workflows/pr-summary.yml — 200+ lines
name: PR Summary
on: pull_request
jobs:
  summarize:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Get diff
        run: git diff origin/main...HEAD > diff.txt
      - name: Call OpenAI
        run: |
          curl https://api.openai.com/... \
            -d @prompt.json > out.json
      - name: Parse response
        run: jq -r '.choices[0].text' out.json > comment.md
      - name: Post comment
        uses: actions/github-script@v7
        with:
          script: |
            const fs = require('fs');
            const body = fs.readFileSync('comment.md', 'utf8');
            github.rest.issues.createComment({ ... })
      # ... and 150 more lines of error handling
Most of the team has written something like this. Get a nod. Then say: "What if you didn't have to?"
0:09 – 0:15 · English, not YAML

The new way

# pr-summarizer.md — the whole thing
---
on: pull_request
engine: claude
tools:
  github: { allowed: [get_pull_request_diff, list_commits] }
safe-outputs:
  add-comment: { max: 1 }
---

# PR Summarizer

Read the PR diff and post ONE comment with:
- **What changed** — 2-3 sentences
- **Risk callouts** — 🔴 high / 🟡 medium / 🟢 low
- **Test coverage** — gaps?
- **Suggested next steps** — up to 3 items

That's the whole workflow. ~25 lines.

Pause here. Let the difference sink in. Then say: "The .lock.yml that gets generated is still 1000+ lines — but you don't write it, you don't read it, you don't debug it."
0:09 – 0:15 · English, not YAML

Anatomy of an agentic workflow

SectionWhat it controlsExample
on: When does it run? pull_request, schedule, issues
engine: Which AI model claude, copilot, codex
permissions: What GitHub access contents: read
tools: What the agent can do github, bash, MCP servers
safe-outputs: What it's allowed to produce add-comment, create-issue
Body The prompt itself Plain markdown instructions
Don't read every row. Highlight "tools" and "safe-outputs" — these are the security model. The agent CANNOT do anything not listed in tools, and CANNOT produce anything not in safe-outputs.
0:09 – 0:15 · English, not YAML

Why safe-outputs change everything

Without safe-outputs

Agent has a GitHub token. It can do anything the token allows: push to main, force-delete branches, leak secrets.

With safe-outputs

Agent runs in a sandboxed job with no token. It writes intent to a file (e.g. "post this comment"). A separate job validates and executes it.

Translation: even a prompt-injection attack can't make the agent push code.

This is THE security pitch. It's also what makes gh-aw different from "give Claude an API token and hope". Security team will love this slide.
