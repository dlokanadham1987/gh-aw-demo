What is an agentic workflow?

What is an agentic workflow?

A regular GitHub workflow you'd write in YAML — except instead of writing commands, you write an English prompt, and an AI agent figures out what to do at runtime.

📅 Triggered by

PR opened, schedule, issue created — same events as any workflow.

🤖 Run by

An AI agent (Claude / Copilot / Codex) executing your written intent.

✅ Constrained by

Allow-listed tools and safe-outputs — agent can't go off-script.

Examples: "Review every PR for security issues" · "Open a daily issue summarising yesterday's test failures" · "Auto-label PRs based on what files changed"

One-line definition first. Then concrete examples. Stress: an agentic workflow IS a GitHub workflow — same triggers, same runners — with one new ingredient (the AI engine).
What is an agentic workflow?

Plain YAML vs Agentic .md

Plain workflow (.yml)

  • You write every step explicitly
  • Hard-coded commands, shell scripts
  • Predictable, deterministic
  • ~200 lines for non-trivial tasks

Agentic workflow (.md)

  • You write the goal; agent picks the steps
  • Plain-English prompt + allow-listed tools
  • Adapts to the input each run
  • ~25 lines for the same task

Both live in .github/workflows/. Both run on the same GitHub Actions runners. The difference is who decides the steps — you, or the agent.

Same family. Same triggers. Same runners. Same security boundaries. Only the "how it gets the work done" changes — and that's the entire value prop.

Mental model

The two Claudes — don't confuse them

🧑‍💻 Author-time Claude (Claude Code)

Lives in your IDE.

  • Helps you write the workflow .md
  • Loads your .claude/ subagents & skills
  • Never runs in CI

🤖 Runtime Claude (gh-aw agent)

Lives in a sandboxed GitHub runner.

  • Executes the workflow when it fires
  • Uses ANTHROPIC_API_KEY repo secret
  • Sees only what your .md exposes

Two completely different processes. The Claude that helped you write the prompt is not the same Claude that runs the prompt.

#1 source of confusion. Calling this out early prevents a dozen "but I configured my Claude Code…" questions. Sets up Demo 2 — bridging the two via imports:.
Mental model

Two files. Three commands.

📝 What you author

pr-summarizer.md — frontmatter + prompt body. ~25 lines.

⚙️ What runs

pr-summarizer.lock.yml — generated by gh aw compile. ~1000+ lines. Don't edit.

The three commands

# 1. One-time per repo
gh aw init

# 2. Add or write a workflow
gh aw add pr-summarizer

# 3. Whenever the .md changes
gh aw compile pr-summarizer

Think package.json + package-lock.json. You author one, the tool maintains the other.

Three commands cover 95% of usage. The .md/.lock.yml split is reproducibility insurance: what runs in CI is exactly what's reviewed in the PR.
Anatomy of the .md file

Anatomy of the .md file — overall

---  ← frontmatter starts
name: PR Summarizer
on:
  pull_request:
    types: [opened, synchronize]
engine: claude
permissions:
  contents: read
  pull-requests: write
tools:
  github:
    allowed: [get_pull_request_diff, list_commits]
safe-outputs:
  add-comment: { max: 1 }
---  ← frontmatter ends

# PR Summarizer  ← body starts (the prompt)

Read the PR diff and post ONE comment with:
- **What changed** — 2-3 sentences
- **Risk callouts** — 🔴 / 🟡 / 🟢
- **Test coverage** — gaps?
- **Suggested next steps**

Two parts: frontmatter (configuration in YAML) and body (the prompt in English).

Anatomy — the frontmatter fields

FieldWhat it controlsRequired?
on: When does it run? (PR, schedule, issue, manual) ✅ Yes
engine: Which AI engine — claude / copilot / codex ✅ Yes
permissions: What GitHub scopes the run gets 🟡 Strongly recommended
tools: What the agent can call — github MCP, bash, web-fetch 🟡 Strongly recommended
safe-outputs: What the agent is allowed to produce — comments, PRs, labels 🟡 Strongly recommended
imports: Shared .md content (e.g. from .claude/) ⚪ Optional

Frontmatter is the contract: when, who, with what tools, producing what.

Don't read every row. Emphasize tools + safe-outputs — they're the security model. Mention imports: briefly here — it's the bridge to .claude/ that we'll see in Demo 2.
Anatomy of the .md file

Anatomy — the body (your prompt)

# PR Summarizer

You are reviewing a pull request. Post ONE comment with these sections:

1. **What changed** — short plain-English summary
2. **Files touched** — high-level map of areas affected
3. **Risk callouts** — 🔴 high / 🟡 medium / 🟢 low
4. **Test coverage** — flag any missing tests
5. **Suggested next steps** — concrete reviewer actions

Use markdown headings and bullet points. Keep it under 400 words.
  • Pure markdown — no YAML, no code.
  • This is what Claude sees at runtime, alongside the PR diff (fetched via tools).
  • Iterate freely. Body edits don't require recompile — just commit and push.
The body is just markdown. No magic. Anything you'd tell a junior reviewer in writing goes here. Be specific about format, set hard limits, say what NOT to do.
How it runs

What runs, step by step

1. Event fires (PR opened, push, schedule, …)
↓
2. GitHub Actions reads *.lock.yml and starts a runner
↓
3. activation: pulls your prompt + sets up Claude
↓
4. agent: Claude reads context, calls allowed tools
↓
5. safe_outputs: validate & execute the agent's intent
↓
6. conclusion: post the comment / open the PR / etc.
6 sequential jobs. You don't memorize them — but you'll see them in the Actions UI as 6 boxes. Helpful for debugging: when something fails, the job name tells you WHERE.
How it runs

Why safe-outputs change everything

Without safe-outputs

Agent has a GitHub token. It can do anything the token allows: push to main, force-delete branches, leak secrets.

With safe-outputs

Agent runs in a sandboxed job with no write token. It writes intent to a file ("post this comment"). A separate job validates and executes only what you allow-listed.

Translation: even a prompt-injection attack can't make the agent push code.

THE security pitch. Brain has no hands. Safe-outputs is what makes gh-aw production-safe vs "give Claude a token and hope."
Step-by-step creation

How YOU create one — the 9-step loop

Setup (once)

  1. Install gh-aw extension
  2. Run gh aw init in repo
  3. Set ANTHROPIC_API_KEY as repo secret

Author

  1. Write .md (frontmatter + body)
  2. Run gh aw compile <name>
  3. Commit BOTH .md and .lock.yml

Ship & iterate

  1. Push to default branch (auto-registers)
  2. Trigger it (open a PR, run schedule, etc.)
  3. Watch logs, refine prompt, repeat

The loop is the same for every workflow you'll ever build.

Steps 1-3 are one-time. Steps 4-6 happen each time you author. Steps 7-9 are the ongoing loop. Reassure: ~10 minutes for the first one if all prereqs are met.
Step-by-step creation

Steps 1–4 — set up & author

# Step 1 — Install the extension (one-time, per machine)
gh extension install githubnext/gh-aw

# Step 2 — Initialize in your repo (one-time, per repo)
cd path/to/your/repo
gh aw init

# Step 3 — Set the API key as a repo secret
gh secret set ANTHROPIC_API_KEY
# (paste sk-ant-… when prompted)

# Step 4 — Author the workflow source file
# Either pull a template:
gh aw add pr-summarizer

# Or hand-write .github/workflows/<name>.md (see anatomy slides)
Steps 1-3 are one-time scaffolding. Step 4 is where the actual workflow design happens. Most teams use `gh aw add` for the first one (templates) and hand-write later.
Step-by-step creation

Steps 5–9 — compile, ship, iterate

# Step 5 — Compile .md → .lock.yml (deterministic, no AI)
gh aw compile pr-summarizer

# Step 6 — Commit BOTH files together
git add .github/workflows/pr-summarizer.md \
        .github/workflows/pr-summarizer.lock.yml \
        .github/aw/actions-lock.json
git commit -m "Add PR Summarizer agentic workflow"

# Step 7 — Push to the default branch
git push   # workflow auto-registers when on default branch

# Step 8 — Trigger it (open any PR)
gh pr create --title "Test workflow" --body "Triggering it"

# Step 9 — Watch logs & iterate
gh run watch

To change the prompt later: edit the .md body → commit → push. No recompile needed for body-only edits.

Critical: commit BOTH files. The most common day-one mistake is forgetting the .lock.yml. Once shipped, iteration is fast — body edits don't require recompile.

Demo 2 · Reusing .claude/ subagents

Demo 2 — what if we could reuse work?

Many teams have already invested in Claude Code subagents and skills inside .claude/ — security reviewers, style checkers, triage agents that devs use locally in their IDE.

Question: can the same prompt that helps your dev locally also run automatically on every PR in CI?

Answer: yes — via imports: in the workflow frontmatter.

Hook the audience: they've already built useful prompts. Don't make them rewrite them for CI. The bridge is one line of frontmatter.
Demo 2 · Reusing .claude/ subagents

The bridge — imports:

📁 .claude/agents/security-reviewer.md
Your existing Claude Code subagent — used locally in the IDE
↓ imports: pulls it in at compile time
📝 .github/workflows/security-review.md
New agentic workflow — references the same prompt
↓ gh aw compile
⚙️ security-review.lock.yml
Generated YAML with the imported prompt baked into the assembled system prompt

One source of truth for the prompt. Update .claude/agents/security-reviewer.md once; both your IDE and CI pick it up.

imports: is a compile-time directive. At gh aw compile, the imported file's content gets stitched into the assembled system prompt. The runtime agent sees it as part of its instructions.
Demo 2 · Reusing .claude/ subagents

The workflow file — Security Reviewer

# .github/workflows/security-review.md
---
name: Security Reviewer
on:
  pull_request:
    types: [opened, synchronize]
engine: claude
permissions:
  contents: read
  pull-requests: write
imports:
  - .claude/agents/security-reviewer.md  ← reuse the IDE subagent
tools:
  github:
    allowed: [get_pull_request_diff, get_pull_request_files]
safe-outputs:
  add-comment: { max: 1 }
  add-labels: { max: 3 }
---

# Security Reviewer

Apply the security-reviewer rules imported above to this PR's diff.
Post ONE comment summarizing findings. Apply labels:
- `security:high` for any 🔴 finding
- `security:review` if any 🟡 findings exist

~20 lines. Reuses an existing subagent. Adds CI automation on top.

Point out: imports: line is THE bridge. Everything else is standard workflow frontmatter. The body is short because the heavy lifting is in the imported subagent.

The payoff — one prompt, two surfaces

🧑‍💻 In your IDE

Developer asks Claude Code: "Run the security reviewer on this branch."

Loads .claude/agents/security-reviewer.md automatically.

🤖 In CI on every PR

Agentic workflow imports the same file, runs automatically when a PR opens.

Same prompt, same standards, no duplication.

Update the prompt once → both surfaces benefit. That's the org-wide payoff of agentic workflows on top of Claude Code investments.

Make the value prop explicit: this is org-wide reuse. Skills/subagents you built for individuals become CI automation for everyone. Single source of truth.
